# Apex Dashboard 文件结构分析

## 证据与隐私边界

本分析只读检查了用户指定的本地 Vault 中的一份 Dashboard Markdown、已安装的 Apex Dashboard 1.4.4 插件清单和打包源码。Dashboard 位于 Vault 内，由插件设置指向；插件代码与设置位于 Vault 的 `.obsidian/plugins/apex-dashboard/` 下。这里仅记录相对结构和语法，不记录 Vault 的绝对路径、真实列名、卡片标题、任务文本、配置值或凭据。

以下“样本观察”只代表检查时的文件；“插件行为”只代表已安装版本。两者都不是所有 Obsidian Vault 的通用格式。

## 样本观察

| 层级 | 观察到的形式 | 对 Pulse 的含义 |
| --- | --- | --- |
| 文件头 | YAML frontmatter，以 `---` 包围；包含 `dashboard: true`、`banner`、`columns` | `dashboard: true` 是候选文件校验信号；banner 与任务读取无关。 |
| 列定义 | `columns` 数组，每项包含 `name`、`color`、`type` | 顺序决定页签顺序；颜色是展示提示，类型不能从名称猜测。 |
| 列正文 | 行首 `##` 标题 | 每个标题对应一个列；本样本有 3 列，类型为两个 `todo`、一个 `projects`。 |
| 卡片 | 列内的行首 `###` 标题，随后有 `id:`、`type:` 元数据 | 卡片属于其所在列；本样本有 4 张卡片，另有一个空列。`id` 是卡片标识，不是任务 ID。 |
| 任务 | 卡片内 `- [ ]` 与 `- [x]` 行 | 分别表示未完成和已完成；首版仅展示，不改变标记。 |

样本中一个备忘类卡片位于待办列内。因此 Pulse 的顶部页签应映射列，卡片标题应留在对应页签内部，不能把卡片标题自动提升为页签。

## 元数据、标签与日期

- 观察到的卡片元数据只有 `id` 和 `type`；没有任务级独立 ID。
- 未观察到任务标签、日期、提醒标记、嵌套复选框或 Markdown block identifier。不能把“未出现”写成“插件不支持”。
- 已安装插件的任务解析代码接受普通 `[ ]`、`[x]`／`[X]` 标记，并识别尾部的 `⏰ YYYY-MM-DD HH:mm` 提醒与 `<!--collapsed-->` 标记。这是插件能力观察，**不是**本样本的字段，也不进入首版日期或提醒语义。
- `#tag` 若将来出现在任务文本中，首版应作为原始文本展示；没有证据表明此 Dashboard 为它提供独立的标签字段。

## 插件读写行为与设计影响

已安装版本先读取 YAML 与 `##`／`###` 正文，形成列、卡片和任务。插件对任务勾选后会重新序列化并写入**整份** Dashboard 文件，同时尝试在隐藏备份目录保存旧内容。顶层任务完成时还可能改变任务在卡片内的顺序。Pulse 不能把行号或任务序号当作跨刷新稳定 ID，也不能在未来写回时假设外部编辑只改动一行。

本阶段没有对个人 Vault 进行写入。可公开提交的虚构格式样本位于 [`Tests/Fixtures/sample-apex-dashboard.md`](../Tests/Fixtures/sample-apex-dashboard.md)。
